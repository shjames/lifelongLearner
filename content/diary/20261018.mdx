今天整理了一份 TCP 的交互演示页面，存进了博客。

👉 [打开交互演示：TCP 连接的建立与关闭](/diary/tcp-handshake-teardown.html)

单文件 HTML，深色主题，没有任何外部依赖，双击就能在浏览器里跑。

## 它怎么演示

页面中间分成左右两半：左边客户端，右边服务端，各自显示当前的**状态**、`snd.nxt`（下一个要发送的序号）和 `rcv.nxt`（下一个期望接收的序号）。两个方块之间是报文气泡，标着 SYN、ACK、数据、FIN、RST，虚线表示重传或旧报文。

核心设计是：**每点一次「下一步」，就发出一条报文。** 两侧的状态和 seq / ack 会同时更新，按 TCP 的真实规则走。

为了便于阅读，演示用 100、300 这类小数字代替随机的 32 位初始序号，但报文顺序和状态转换遵循 RFC 9293。

配套的操作有：上一步、重试本步、自动播放、重置、速度调节。还有个开关专门用来**模拟最后一条 ACK 丢失**——用来观察 TIME_WAIT 为什么存在。TIME_WAIT 的 2MSL 倒计时做成了加速版，真实 Linux 下大约 60 秒。

## 两个对比实验

**实验一：为什么两次握手不够。**

场景设得很巧：客户端曾经发起过一次连接，SYN 在网络里滞留；客户端已经放弃这次连接并回到 CLOSED。现在这条旧 SYN 才姗姗来迟。

切换右侧的握手模式（三次握手 / 两次握手假设），看服务端的结局。结论落成两条：

- 序号没有双向确认。服务端发出自己的 ISN 后，没有任何报文能证明客户端收到了它，三次握手的第三条 ACK 才补上这一环
- 无法识别过期的连接请求。迟到的旧 SYN 会让两次握手的服务端单方面建立连接，而客户端根本不在建连状态

两条都满足，就必然需要三条报文：两个方向各一次「报序号 + 被确认」。

**实验二：挥手一定是四次吗。**

区别只在于被动关闭方收到 FIN 时，手里还有没有数据要发。没有剩余数据时，ACK 与 FIN 合并成一条，实际只看到三条报文。

## 六个常见误区

页面里列了六条，每条都给了纠正：

| 误区 | 纠正 |
|---|---|
| 三次握手保证了数据可靠 | 握手只对齐双方的初始序号，可靠性来自序列号、确认、重传和校验和 |
| 握手完成 = 服务端已经处理了请求 | 握手只到内核，业务代码要等 HTTP 请求交给应用之后才开始执行 |
| 四次挥手一定发四条报文 | 被动方没有剩余数据时，ACK 与 FIN 会合并，实际是三条 |
| FIN 之后连接就断了 | FIN 只关闭发送方向，接收方向仍可用，这叫半关闭 |
| TIME_WAIT 是网络故障 | 它是协议规定的正常状态；数量过多是一个症状，要看短连接为什么多、谁在主动关闭 |
| 连接是一条端到端的线 | 连接是两端内核各自保存的一组状态，四元组相同才算同一条连接 |

## 和前端的关系

这部分给了一条首屏的往返示意：

```
DNS  →  TCP 握手（1 RTT）  →  TLS（1–2 RTT）  →  HTTP 请求/响应
```

然后对应到三个优化方向：

- **keep-alive / 连接池**：复用已建立的连接，省掉后续握手
- **HTTP/2 多路复用**：一个 TCP 连接上并发多个请求，不必每个请求都建一条
- **HTTP/3 走 QUIC（基于 UDP）**：把传输握手与 TLS 握手合并，首次 1 RTT、会话恢复可 0 RTT，绕开的正是 TCP + TLS 串行握手的开销

页面里还有一句自测题值得记：**HTTP/2 解决了应用层的队头阻塞，没解决 TCP 层的**——一个 TCP 段丢失，所有 stream 都得等重传，这个要靠 HTTP/3/QUIC 的独立 stream 解决。

最后一章有几句写得很实在：

- 不要照抄网上的「优化参数」，尤其不要启用 `tcp_tw_recycle`（已移除，NAT 下有害）
- 「先定位问题，再改参数，并记录基线」
- CLOSE_WAIT 堆积**几乎总是应用层问题**：对端已发 FIN，内核回了 ACK，但应用没有调用 `close()`；网络层通常没问题

## 一点体会

学 TCP 卡住的地方，往往不是记不住那几个状态名，而是**状态本身是隐形的**——抓包抓到的是离散的报文，但真正在变化的是两端各自内核里的一台机器。文字描述永远是「收到 SYN 之后进入 SYN_RCVD」这种时序叙事，读的时候以为懂了，一合上书就散了。

这个页面的做法正好补上这一块：**同一时刻把两侧的 (状态, snd.nxt, rcv.nxt) 并排摆在屏幕上**，每发一条报文，两边一起动。状态不再是名词，而是一个可以被观察的位置。

另一个让我觉得设计得好的地方，是它不满足于「告诉你三次握手」，而是专门设了实验回答**为什么不能是两次**。背结论记住的是流程，做一次反例实验记住的是原因——后者才不会被下一次换个场景就忘掉。

就像那句自测题的价值：能回答问题不算掌握，能对照抓包指出对应字段才算。判断标准落到了「能不能在真实数据里找到它」。
