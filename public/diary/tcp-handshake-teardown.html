实验一：为什么两次握手不够

场景：客户端曾经发起过一次连接，SYN 在网络里滞留；客户端已经放弃这次连接并回到 CLOSED。现在这条旧 SYN 才到达服务端。切换右侧的握手模式，看服务端的结局有什么不同。

六个常见误区

✕

「三次握手保证了数据可靠。」握手只对齐双方的初始序号。可靠性来自序列号、确认、重传和校验和。

✕

「握手完成 = 服务端已经处理了请求。」握手只到内核。业务代码要等 HTTP 请求抵达并交给应用之后才开始执行。

✕

「四次挥手一定发四条报文。」被动方没有剩余数据时，ACK 与 FIN 会合并成一条，实际是三条。

✕

「FIN 之后连接就断了。」FIN 只关闭发送方向，接收方向仍然可用，这叫半关闭。实验一的第 7 步演示了这一点。

✕

「TIME_WAIT 是网络故障。」它是协议规定的正常状态，出现在主动关闭方。数量过多是一个症状，要看短连接为什么多、谁在主动关闭。

✕

「连接是一条端到端的线。」连接是两端内核各自保存的一组状态。四元组（源 IP、源端口、目的 IP、目的端口）相同，才算同一条连接。

和前端的关系

一次 HTTPS 首屏的往返示意：

DNS TCP 握手 · 1 RTT TLS · 1–2 RTT HTTP 请求/响应

示意图，宽度不按真实比例；RTT 数量取自协议流程，实际耗时取决于网络与服务器。

  • keep-alive / 连接池：复用已建立的连接，省掉后续的握手。
  • HTTP/2 多路复用：一个 TCP 连接上并发多个请求，不必每个请求都建一条。
  • HTTP/3 走 QUIC（基于 UDP）：把传输握手与 TLS 握手合并，首次 1 RTT，会话恢复可 0 RTT，绕开的正是 TCP + TLS 串行握手的开销。

线上排障信号：CLOSE_WAIT 堆积通常是应用没有调用 close()；TIME_WAIT 过多说明本机是大量短连接的主动关闭方；SYN_RCVD 大量堆积要排查 SYN flood。

1. 基础与封装

先建立「数据在网络里被一层层包起来」的图像，后面读字段才不会迷路。

TCPTransmission Control Protocol · 传输控制协议

定义：传输层的面向连接、可靠、全双工的字节流协议。它为两个进程提供一条双向字节通道，并负责排序、去重、确认、重传和流量控制。

它不负责：不保留应用层消息边界，不负责加密（TLS 负责），也不保证对方业务代码已经处理。握手完成只代表内核状态就绪。

在本页：两个主机之间所有报文、状态和 seq/ack 变化都是 TCP 的行为。

TCP 报文段、IP 包与以太网帧Segment / Datagram / Frame

定义：协议数据单元（PDU）在不同层的叫法。传输层叫报文段（segment），网络层叫 IP 数据报（datagram），链路层叫帧（frame）。

封装关系：以太网头 14 字节 + IP 头 20 字节 + TCP 头 20~60 字节 + 数据。TCP 报文段整体是 IP 包的载荷。

边界：「报文」在日常语境里常被混用。严格说，本页动画画的是 TCP 报文段；抓包软件展示的是解封装后的各层。

四元组与连接4-tuple / Connection

定义：一条 TCP 连接由源 IP、源端口、目的 IP、目的端口唯一标识。连接不是网络里的一条线，而是两端内核各自维护的一组状态和缓冲区。

因此：同一对 IP 之间可以有多条连接，只要端口不同；NAT 会改写地址和端口，并用连接跟踪表维护映射。

在本页：客户端与服务端各保存一份状态；「关闭」删除的是各自的状态记录。

端口Port

定义：16 位整数（0–65535），用来区分同一台主机上的不同进程。服务端通常监听固定端口（如 443），客户端由内核分配临时端口。

IANA 分段：0–1023 知名端口；1024–49151 注册端口；49152–65535 动态/私有端口。Linux 临时端口范围由 ip_local_port_range 决定，常见 32768–60999。

排障：短连接过多会耗尽临时端口，表现为 Cannot assign requested address；这不是带宽问题。

套接字Socket

定义：操作系统提供给应用的编程接口。监听套接字（listen socket）负责接收新连接；accept() 返回一个新的已连接套接字，双方用它收发数据。

本页对应：「客户端」「服务端」两个方块可以理解成两个已连接套接字；服务端的 LISTEN 是监听套接字。

边界：关闭监听套接字不等于关闭已建立的连接；close() 一个已连接套接字才会触发 FIN（或 RST，取决于选项）。

字节流、全双工、面向连接、可靠Byte Stream / Full-duplex / Connection-oriented / Reliability

字节流：TCP 把数据看成连续字节，不保留 write() 的边界。一次写入可能被拆成多个报文段，多次写入也可能合并。应用层必须自己定界（长度前缀、分隔符、HTTP 的 Content-Length/chunked）。

全双工：两个方向独立，各自有 seq、窗口和关闭状态，所以才有半关闭。

可靠：靠序号、确认、校验和、超时重传、去重和排序共同实现，不是靠某一条报文。

MTU、MSS 与路径 MTU 发现Maximum Transmission Unit / Maximum Segment Size / PMTUD

MTU：链路层一次能承载的最大 IP 包大小，以太网常见 1500 字节。MSS：TCP 载荷的最大长度，通常 = MTU − IP 头 − TCP 头 = 1500 − 20 − 20 = 1460。

协商：双方在 SYN 的选项里各自声明 MSS，实际发送取较小值。中间链路 MTU 更小时，靠 PMTUD 或 IP 分片处理。

边界：MSS 是 TCP 层概念，MTU 是链路层概念；说「MSS 1500」是常见错误。

RTT、RTO、MSL 与 2MSLRound-Trip Time / Retransmission Timeout / Maximum Segment Lifetime

RTT：一个报文往返所需时间。RTO：发出数据后等待 ACK 的超时时间，按 RTT 动态估算（RFC 6298），拥塞时会指数退避。

MSL：报文在网络中允许存活的最长时间。2MSL：TIME_WAIT 的等待时长，确保最后一个 ACK 能重发、旧报文能过期。

实现差异：Linux 的 TIME_WAIT 固定约 60 秒；tcp_fin_timeout 控制的是 FIN_WAIT_2，不是 TIME_WAIT。

序号Sequence Number · seq

定义：32 位无符号数，表示本报文段第一个数据字节在发送方字节流中的编号。若本报文段不带数据，序号仍是发送方当前的 SND.NXT。

消耗规则：数据消耗 len 个序号；SYN 消耗 1 个；FIN 消耗 1 个；纯 ACK 不消耗。因此 SYN(seq=100) 之后，下一次发送的序号是 101。

回绕：按 2³² 取模。比较新旧序号不能用简单数值大小，协议用模运算判断。

确认号Acknowledgment Number · ack

定义：期望收到的下一个字节编号，等于「已连续收到的最后一个字节 + 1」。它确认的是这个编号之前的所有字节，而不是某一条报文。

有效条件：只有 ACK 标志位为 1 时才有效。接收方只接受 SND.UNA < ack ≤ SND.NXT 的确认，不能确认还没发出去的数据。

例子：客户端 SYN 占掉 100，所以服务端回 ack=101；服务端发 200 字节 seq=301，客户端回 ack=501。

数据偏移与保留位Data Offset / Reserved

数据偏移：4 位，单位是 4 字节。值 5 表示 20 字节，值 15 表示 60 字节。它告诉接收方「头部到此为止，后面是数据」。

保留：RFC 9293 定义为 4 位，必须置 0。老教材里可能画成 3 位或 6 位，这是历史版本差异；读报文时以实际位宽为准。

组合示例：0x02 = SYN；0x12 = SYN+ACK；0x10 = ACK；0x11 = FIN+ACK；0x18 = PSH+ACK。

SYNSynchronize Sequence Numbers

作用：同步初始序号。SYN=1 表示「这是我的起始序号，请从这里开始编号」，同时告诉对方自己希望使用的连接参数（MSS、窗口缩放等）。

规则：SYN 消耗 1 个序号；SYN+ACK 同时完成「报自己的 ISN」和「确认对方 ISN」。普通握手通常不在 SYN 里带数据；TCP Fast Open 是例外。

攻击面：只发 SYN 不回 ACK 会留下半开连接，形成 SYN flood；防御手段包括 SYN 队列、SYN cookies、限速。

ACKAcknowledgment

作用：确认对方的数据。ACK=1 时确认号字段有效；除了第一个 SYN，几乎所有报文都会置 ACK。

捎带确认：有数据要发时，ACK 可以和数据合并在同一报文里，不必单独发。纯 ACK 不消耗序号。

延迟确认：接收方可能等一小段时间（Linux 常见 40–200 毫秒）再确认，期望捎带在回程数据里，减少报文数；与 Nagle 同时出现时可能造成可感知延迟。

FINFinish

作用：发送方没有更多数据了，关闭自己的发送方向。对方仍可继续发送，这叫半关闭。

规则：FIN 消耗 1 个序号，所以需要被确认；未确认会重传。FIN 通常与 ACK 合并。

边界：FIN 不等于连接立即消失；主动关闭方还要经过 FIN_WAIT_1/2 和 TIME_WAIT。

RSTReset

作用：立即复位连接，表示「这个连接不成立或不能继续」。收到 RST 的一方直接删除状态，不走四次挥手。

常见触发：端口没有监听；收到不属于任何连接的数据；应用崩溃；SO_LINGER 设为 0 后 close；半开连接上收到数据；中间设备超时后主动发 RST。

前端现象：浏览器报 ERR_CONNECTION_RESET 或 ECONNRESET，通常是连接被重置，不是 DNS 或证书问题。

PSH 与 URGPush / Urgent

PSH：提示接收方尽快把数据交给应用，不要等待填满缓冲区。它不是消息边界，现代实现经常自动设置或忽略，不能用来分帧。

URG + 紧急指针：标记紧急数据的位置。实际使用极少，且不同实现行为不一致；新协议不应依赖。

ECE 与 CWRECN-Echo / Congestion Window Reduced

背景：ECN（显式拥塞通知）。路由器在拥塞时标记报文，而不是直接丢包。

ECE：接收方回显「我收到了拥塞标记」；CWR：发送方表示「我已经减小拥塞窗口」。二者在 SYN 中协商是否启用。

本页未演示：它属于拥塞控制，不影响握手和挥手的主线。

窗口Window

定义：16 位接收窗口，表示「从确认号开始，我还能接收多少字节」。它是流量控制，不是拥塞控制。

扩展：窗口缩放选项把 16 位左移最多 14 位，突破 65535 字节限制。零窗口表示接收缓冲区满，发送方停止发送并周期性发窗口探测。

注意：抓包里的窗口值可能已经被缩放；Wireshark 会分别显示原始值和计算值。

校验和与伪头部Checksum / Pseudo-header

计算范围：伪头部（源 IP、目的 IP、协议号、TCP 长度）+ TCP 头部 + 数据，按 16 位反码求和。

作用：检测比特错误，不提供认证，也不防篡改。接收方校验失败通常直接丢弃，不回复。

抓包注意：启用校验和卸载（checksum offload）时，本机抓到的出站报文校验和可能显示错误，这是网卡还没计算，不代表链路出错。

选项TCP Options

常见选项：MSS（最大段长度）、SACK permitted（允许选择确认）、Timestamps（RTT 测量与 PAWS）、Window Scale（窗口缩放）、NOP/EOL（对齐填充）。

长度：最多 40 字节，所以 TCP 头最大 60 字节。选项通常出现在 SYN 中；建立后不一定每条都带。

3. 序号、确认与可靠性

这一节解释「为什么丢包了还能恢复」「为什么 ack 不能跳过缺口」「窗口到底限制了什么」。

ISN 初始序号Initial Sequence Number

定义：每条连接、每个方向随机选择的初始序号。真实值是 32 位随机数，例如 2893451234；本页用 100 和 300 只是方便心算。

为什么随机：防止旧连接的报文被新连接误收，也提高攻击者猜测序号的难度（RFC 6528）。

规则：SYN 本身占用 ISN 这一个序号，所以第一个数据字节从 ISN+1 开始。

四个关键变量SND.UNA / SND.NXT / SND.WND / RCV.NXT

SND.UNA：最早一个已发送但未确认的序号。SND.NXT：下一个要发送的序号。SND.WND：发送窗口。RCV.NXT：下一个期望接收的序号。

关系：已发送未确认的字节数 = SND.NXT − SND.UNA；它不能超过对方通告的窗口。收到合法 ACK 后 SND.UNA 前移。

在本页：界面上的 snd.nxt / rcv.nxt 就是其中两个变量。

累计确认Cumulative Acknowledgment

定义：ack=n 表示「n 之前的所有字节都收到了」。即使中间有乱序到达的更高序号，也不能越过缺口确认。

例子：收到 1–100 和 201–300，但 101–200 缺失，ack 仍然停在 101；发送方会重传 101–200。

与 SACK 的区别：SACK 只告诉发送方「哪些块收到了」，ack 字段仍表示连续前缀，不会跳过缺口。

选择确认SACK · Selective Acknowledgment

定义：选择确认扩展（RFC 2018）。接收方在选项里报告已收到的离散块，发送方只重传缺失部分。

协商：双方在 SYN 中交换 SACK permitted 选项；没协商成功就不能用。

抓包：Wireshark 的 TCP 选项里会显示 SACK blocks，例如 left edge / right edge。

重复 ACK 与快速重传Duplicate ACK / Fast Retransmit

重复 ACK：接收方反复收到乱序报文，每次都回同一个 ack（缺口位置）。

快速重传：发送方连续收到 3 个重复 ACK，就认为该段丢失，立即重传，不等 RTO 到期（RFC 5681）。

边界：3 是经典阈值；SACK、重复报文和乱序都可能影响判断，抓包里要结合序列号看。

滑动窗口与流量控制Sliding Window / Flow Control

发送窗口：发送方在未收到确认前最多能发出的字节数，取「拥塞窗口 cwnd」和「接收窗口 rwnd」的较小值。

滑动：收到 ACK 后窗口左边界右移，新的序号进入可发送范围，所以叫滑动窗口。

流量控制：接收方通过窗口字段限制发送方，防止自己的缓冲区被淹没。窗口为 0 时发送方暂停，并定期发零窗口探测。

超时重传与 RTORetransmission / Retransmission Timeout

机制：发送数据时启动重传定时器；在 RTO 内没收到确认就重传，并指数退避（RTO 翻倍）。

RTO 估算：用 RTT 的平滑值和偏差计算（RFC 6298），不是固定值。网络抖动大时 RTO 会变大。

边界：重传的报文序号不变；接收方靠序号去重。超时重传和快速重传是两条不同的路径。

拥塞控制Congestion Control

定义：发送方根据网络拥塞程度调整发送速率，避免把网络压垮。核心变量是 cwnd（拥塞窗口）和 ssthresh（慢启动阈值）。

四个阶段：慢启动（cwnd 指数增长）→ 拥塞避免（线性增长）→ 快速重传/快速恢复 → 超时后回到慢启动。经典算法是 Reno，现代内核常用 CUBIC，部分场景用 BBR。

与流量控制的区别：流量控制保护接收方，拥塞控制保护网络。本页只演示握手/挥手，没有展开拥塞控制。

乱序、重复与重组Out-of-order / Duplicate / Reassembly

乱序：报文走不同路径或重传，到达顺序可能与发送顺序不同。接收方按 seq 放入重组队列，等缺口补齐再按序交给应用。

重复：重传可能让同一序号到达两次，接收方按序号去重，并再次确认。

结果：应用看到的是有序、无重复的字节流；代价是乱序期间要占用接收缓冲区。

消息边界与粘包Message Framing / Sticky Packets

问题：TCP 是字节流，send() 一次不等于一个报文段，recv() 一次也不等于一条消息。粘包/拆包是应用层必须处理的现象，不是 TCP 的 bug。

常见方案：固定长度；长度前缀（二进制协议常用）；分隔符（如换行）；自描述格式（HTTP 头 + Content-Length / chunked）。

前端类比：WebSocket 的 message 边界由协议层提供；裸 TCP 没有，需要自己定义。

Nagle 算法与延迟确认Nagle Algorithm / Delayed ACK

Nagle：发送方把小数据攒起来，等前一个未确认数据被确认后再发，减少小包数量。低延迟场景常用 TCP_NODELAY 关闭。

延迟确认：接收方延迟发送 ACK，期望捎带数据。两者叠加可能出现约 40 毫秒的延迟，常见于 request/response 小包场景。

边界：Nagle 是发送方算法，延迟确认是接收方算法；不是所有实现和所有流量都会触发。

4. 连接建立与关闭

这一节把三次握手、四次挥手和所有相关状态放到一起，并解释常见的线上异常。

三次握手Three-way Handshake

流程：SYN(seq=x) → SYN+ACK(seq=y, ack=x+1) → ACK(ack=y+1)。只用 1 个 RTT。

目标：双方各报一次 ISN，并各确认一次对方的 ISN；同时确认双向可达。第三条 ACK 可以携带数据。

为什么不是两次：服务端发出 SYN+ACK 后，无法确认客户端收到了自己的 ISN；迟到的旧 SYN 还可能让服务端单方面建立幽灵连接。

为什么不是四次：SYN 和 ACK 可以合并在一条报文里，第二次握手已经同时完成两件事。

半开连接Half-open Connection

定义：一方认为连接存在，另一方已经不存在（崩溃、断网、超时）。典型是服务端在 SYN_RCVD 或 ESTABLISHED，客户端已经消失。

后果：占用服务端资源；发送数据可能收到 RST；靠 keepalive、超时或应用层心跳清理。

SYN 队列、accept 队列与 backlogSYN Queue / Accept Queue / Backlog

SYN 队列：收到 SYN、还没完成三次握手的连接（SYN_RCVD）。accept 队列：已完成握手、等待应用 accept() 的连接。

backlog：listen(fd, backlog) 的参数，影响队列上限；Linux 还受 net.core.somaxconn 限制。应用 accept 太慢会导致队列满，新连接被丢弃或超时。

排障：SYN_RCVD 多可能是 SYN flood 或队列不足；ESTABLISHED 多但应用没处理，可能是 accept 队列积压。

SYN flood 与 SYN cookiesSYN Flood / SYN Cookies

SYN flood：攻击者大量发送 SYN 但不回最后 ACK，耗尽服务端的半开连接队列。

SYN cookies：服务端不保存半开状态，把连接信息编码进自己的 ISN；收到 ACK 后再重建状态。开启后能缓解队列耗尽，但会丢失部分选项信息。

其他防御：增大 tcp_max_syn_backlog、缩短 SYN 重传、限速、上游清洗。

四次挥手与半关闭Four-way Handshake / Half-close

流程：主动方 FIN → 被动方 ACK → 被动方 FIN → 主动方 ACK。两个方向各关一次，所以是四次。

半关闭：收到 FIN 只表示对方不再发送，本机仍可发送数据；这就是第 7 步还能传 50 字节的原因。

合并：被动方没有剩余数据时，ACK 与 FIN 可以合并成一条 FIN+ACK，抓包里只看到三条，但语义仍是两个方向各自关闭。

TIME_WAIT 与 2MSLTIME_WAIT / 2MSL

谁进入：主动关闭方，在发出最后一个 ACK 后进入 TIME_WAIT，等待 2MSL 才删除连接。

两个作用：① 最后一个 ACK 丢失时，对方会重传 FIN，TIME_WAIT 中还能再回 ACK；② 让这条四元组的旧报文在网络中过期，避免新连接收到残留数据。

实现差异：Linux 约 60 秒；Windows 默认约 120 秒（可配置）。TIME_WAIT 不是错误，数量多要看短连接和主动关闭方。

调优误区：tcp_tw_recycle 在 NAT 环境下会导致连接异常，已在 Linux 4.12 移除，不要使用；tcp_tw_reuse 只影响出站连接复用。

CLOSE_WAITCLOSE_WAIT

含义：被动关闭方收到对方的 FIN 并回了 ACK，但本机应用还没有调用 close()。

堆积原因：应用忘记关闭、连接池泄漏、异常分支没有释放、阻塞在读/写、业务处理太慢。它是应用层问题，不是网络层问题。

处理：检查代码路径和连接池；确认 close()/destroy() 在 finally 中执行；必要时重启泄漏进程并修复根因。

RST 关闭Reset Close

与 FIN 的区别：FIN 是正常关闭，给对方处理时间；RST 是立即终止，可能丢数据。

常见场景：连接不存在、端口未监听、应用崩溃、SO_LINGER=0、半开连接收到数据、负载均衡或防火墙超时。

排查：看 RST 是谁发的、在哪个方向、之前的报文是什么；不要只凭「有 RST」判断是网络故障。

同时打开、同时关闭与 CLOSINGSimultaneous Open / Close / CLOSING

同时打开：双方几乎同时发 SYN，双方都经历 SYN_SENT → SYN_RCVD → ESTABLISHED；实际极少见。

同时关闭：双方几乎同时发 FIN。若在 FIN_WAIT_1 收到对方的 FIN，但自己的 FIN 还没有被确认，就进入 CLOSING；收到对自己 FIN 的 ACK 后再进入 TIME_WAIT。

学习边界：本页只演示「客户端主动关闭、服务端被动关闭」的主线，没有画这两种分支。

TCP keepalive 与 HTTP keep-aliveTCP Keepalive / HTTP Keep-alive

TCP keepalive：内核在连接空闲一段时间后发送探测包，判断对端是否还活着。Linux 默认空闲 7200 秒才开始，通常需要应用层心跳补充。

HTTP keep-alive：复用已建立的 TCP 连接发送多个 HTTP 请求，省掉重复握手。浏览器和服务器通过协议版本/Connection 头协商，空闲超时后关闭。

第三个概念：fetch(..., {keepalive:true}) 是让请求在页面卸载后继续完成，不是 TCP keepalive，也不是 HTTP 连接复用。

SO_LINGER 与 SO_REUSEADDRSocket Options

SO_LINGER：控制 close() 的行为。开启并设超时，close 会等待数据发完；设为 0 会立即发 RST，可能丢数据。

SO_REUSEADDR：允许绑定处于 TIME_WAIT 的本地地址/端口，方便服务重启；不等于允许多个进程同时监听同一端口（那通常是 SO_REUSEPORT）。

边界：这些是套接字选项，不是 TCP 协议字段；不同语言/框架的默认值不同。

状态属于单端，不属于连接整体。同一时刻两端可以处于不同状态；排障时先确认「哪一端、在哪个状态」。

6. 前端与应用

把 TCP 放回一次真实页面加载里：DNS、TCP、TLS、HTTP 各自占多少往返，哪些问题会表现成「接口慢」。

HTTP/1.1 持久连接Persistent Connection / Pipelining

持久连接：HTTP/1.1 默认复用 TCP 连接，响应通过 Content-Length 或 chunked 定界。

队头阻塞：同一连接上请求按序处理，前一个响应慢会挡住后面的响应；浏览器因此对每个域名开多个连接（HTTP/1.1 常见 6 个）。

HTTP/2 多路复用Multiplexing / Stream / HPACK

多路复用：一个 TCP 连接上跑多个 stream，每个 stream 有独立 ID，帧可以交错发送，解决了 HTTP/1.1 的应用层队头阻塞。

仍有 TCP 层队头阻塞：一个 TCP 报文段丢失，内核要等重传，所有 stream 都被挡住；这是 HTTP/3 改走 QUIC 的动机之一。

HPACK：压缩头部，减少重复头部开销。

HTTP/3 与 QUICHTTP/3 / QUIC

传输：基于 UDP，在用户态实现可靠传输、流控制和拥塞控制；TLS 1.3 集成在握手里。

握手：首次 1-RTT，会话恢复可 0-RTT；每个 stream 独立，丢包只影响该 stream，避免 TCP 层队头阻塞；支持连接迁移（换网络不断连）。

注意：QUIC 不是 TCP，本页的握手/挥手不适用；但「可靠传输、序号、确认、窗口」的思想仍然相通。

TLS 握手与往返次数TLS Handshake / RTT

TLS 1.2：完整握手通常 2-RTT（在 TCP 握手之后）。TLS 1.3：1-RTT，支持 0-RTT 会话恢复。

叠加：HTTPS 首屏 = TCP 握手 1 RTT + TLS 握手 + HTTP 请求；HTTP/3 把传输和 TLS 合并，减少往返。

WebSocket 与 SSEWebSocket / Server-Sent Events

WebSocket：通过 HTTP Upgrade 建立，之后是全双工帧协议；底层仍是一条 TCP 连接。适合聊天、协同编辑、实时推送。

SSE：服务器单向推送文本事件流，基于普通 HTTP；自动重连，适合通知、日志流。

边界：WebSocket 的 message 边界是协议层提供的；裸 TCP 没有。

连接池与浏览器并发限制Connection Pool

浏览器：对同一 origin 的并发连接数有限制（HTTP/1.1 常见 6 个；HTTP/2 通常复用 1 条连接）。

服务端连接池：数据库/HTTP 客户端复用连接，减少握手和 TIME_WAIT；池大小要与下游承载能力匹配。

超时对齐：浏览器、负载均衡、服务端的空闲超时不一致，会在复用连接时触发 RST。让上游超时略大于下游，或使用健康检查/重试。

NAT 与端口耗尽NAT / Ephemeral Port Exhaustion

NAT：改写源 IP/端口并维护映射表；表中的条目也有超时。NAT 超时后收到旧连接的数据，可能回 RST。

端口耗尽：大量短连接 + TIME_WAIT 会占满临时端口；表现为无法新建连接。解决方向是复用连接、扩大端口范围、缩短不必要的等待，而不是盲目开启危险的重用选项。

8. 自测与掌握标准

能用自己的话回答下面的问题，并能对照抓包指出对应字段，才算真正掌握。

1. 为什么客户端 SYN 的 seq=100，服务端回的 ack 是 101，而不是 100 或 102？

seq=100 表示客户端的起始序号；SYN 本身占用 1 个序号，所以客户端下一个期望发送的字节是 101。ack 的含义是「下一个期望收到的字节」，因此是 101。100 表示还没收到 SYN 占用的那个号；102 则跳过了 101。

2. 为什么第三条 ACK 发出后客户端立刻 ESTABLISHED，而服务端要等收到它才 ESTABLISHED？

客户端发出 ACK 时，已经确认了服务端的 SYN（ack=y+1），它这一侧的信息完整，所以进入 ESTABLISHED。服务端还没收到这条 ACK，不知道客户端是否收到了自己的 SYN，必须等 ACK 到达才能确认双向就绪。

3. 为什么挥手通常四次，什么情况下三次？

两个方向的关闭独立：主动方 FIN、被动方 ACK、被动方 FIN、主动方 ACK。若被动方收到 FIN 时没有剩余数据，ACK 与 FIN 可以合并成一条 FIN+ACK，于是只看到三条报文。

4. TIME_WAIT 的两个作用是什么？为什么必须在主动关闭方？

① 最后一个 ACK 可能丢失，留在 TIME_WAIT 才能重发；② 让该四元组的旧报文在网络中过期，避免新连接收到残留数据。主动关闭方是最后发送 ACK 的一方，只有它能承担重发和等待旧报文过期的职责。

5. CLOSE_WAIT 堆积是谁的问题？

几乎总是应用层问题：对端已经发 FIN，本机内核回了 ACK，但应用没有调用 close()。常见原因是连接池泄漏、异常分支未释放、阻塞读写。网络层通常没有问题。

6. 纯 ACK 消耗序号吗？它的 seq 字段填什么？

不消耗。纯 ACK 的 seq 字段仍然填写发送方当前的 SND.NXT，但发送后 SND.NXT 不前进；接收方也不会因为纯 ACK 推进 RCV.NXT。

7. 收到乱序报文时，ack 会跳过缺口吗？

不会。累计确认只确认连续前缀；缺口之前的字节即使收到了更高序号，ack 仍停在缺口位置。SACK 可以额外报告已收到的离散块，但不改变 ack 字段的语义。

8. HTTP/2 解决了什么队头阻塞，没解决什么？

解决了 HTTP/1.1 的应用层队头阻塞：多个请求可以交错复用一条连接。没有解决 TCP 层队头阻塞：一个 TCP 段丢失，所有 stream 都要等重传。HTTP/3/QUIC 用独立 stream 解决了后者。

9. MSS 和 MTU 的区别？

MTU 是链路层一次能承载的最大 IP 包大小（以太网常见 1500）；MSS 是 TCP 载荷的最大长度，通常等于 MTU 减去 IP 头和 TCP 头（常见 1460）。MSS 在 SYN 选项中协商。

10. 抓包里看到 RST，如何判断原因？

先看 RST 的方向和它前面的报文：如果服务端在收到数据后回 RST，可能是连接已不存在或端口未监听；如果中间设备超时后回 RST，两侧空闲时间可能不一致；如果应用 close 时设置了 SO_LINGER=0，也会立即发 RST。不要只凭 RST 判断链路故障。

11. socket.end() 和 socket.destroy() 有什么区别？

end() 发送 FIN，进入正常的半关闭/四次挥手流程；destroy() 立即销毁套接字，可能发送 RST，未发送的数据可能丢失。

12. 为什么 TCP 需要应用层自己处理粘包？

TCP 只提供字节流，不保留 write() 的边界。一次写入可能被拆分，多次写入可能合并。应用必须用长度前缀、分隔符或自描述格式来划分消息；这不是 TCP 的缺陷，而是它的设计目标。
